# ASu 金标准写作规范（WangCai 共享参考）

> 本文件提炼自「阿酥版式」示例简历（skill 母版）的写作范式，是 WangCai 全系简历技能
> （audit / polish / maker / jd-match）的内容质量基准。改写或生成经历时**优先按本文件的
> 四段式结构组织**，再叠加各技能的专属流程。
>
> 权威母版：旺财编辑器仓库 `.workbuddy/tmp/asu-skill-demo/ASu示例简历(skill母版).html`。

## 一、核心原则（五条铁律）

1. **真实可核验**：每一条主张都要经得起追问「这是你做的吗？数字怎么来的？」。核不实的指标用 `[~X%]` 标注为估算，或降级表述。
2. **边界清晰**：只写**本人实际完成、提交、上线或维护**的部分。项目是团队的、成果是协作的没关系——写清「我的职责」和「个人边界」，比含糊地霸占整个项目更可信。
3. **三要素齐全**：Owner（项目/模块负责人？）、阶段（0→1 从无到有，还是 1→100 优化迭代）、Scope（多少人 / 多少流量 / 多少营收 / 多少数据）。
4. **每行一个维度**：一行只讲一件事，行首用标签词锚定（见第三节），HR 扫 10 秒能抓到结构。
5. **强动词开头 + 量化收尾**：动作 → 方法 → 结果，没有结果的行动不写或合并。

## 二、条目四段式结构（经历/项目条目默认骨架）

每条经历按以下四段组织（2-4 行，各段一行为主）：

| 段 | 标签词 | 写什么 | 反例 |
|---|--------|--------|------|
| 1. 背景与目标 | `背景与目标：` | 业务/技术痛点一句话 + 目标（写**真实可核验**的优化方向） | 「参与了 XX 项目」 |
| 2. 我的职责 | `我的职责：` / `个人职责：` / `个人贡献：` | Owner 还是模块负责人？负责哪段链路？明确边界 | 「负责相关工作」 |
| 3. 技术实现 | `技术实现：` / `执行链路：` / `关键动作：` | 用了什么 → 解决什么 → 怎么组织（工具链/架构/方法） | 罗列技术名词 |
| 4. 产出与保障 | `工程化：` / `质量保障：` / `协作产出：` / `交付内容：` | 结果 + 沉淀（指标、文档、回归样本、可复用资产） | 「完成了领导交办的任务」 |

示例（ASu 母版风格，虚构内容仅作格式示范）：

```text
背景与目标：为客服和运营团队提供统一的业务问答与流程执行入口，减少重复查询和人工流转。
我的职责：模块负责人，负责意图路由与工具协议的实现和维护。
技术实现：按意图路由检索、订单查询和工单创建等工具，统一结构化输入输出并增加失败重试。
工程化：补充接口文档、测试样例和日志字段，异常定位耗时从小时级降至 10 分钟内。
```

## 三、行首标签词库（按场景取用）

- **背景类**：背景与目标 / 项目简介
- **职责类**：我的职责 / 个人职责 / 个人贡献（三选一，全文统一）
- **实现类**：技术实现 / 执行链路 / 关键动作 / 项目工作 / 技术落地
- **产出类**：工程化 / 质量保障 / 协作产出 / 交付内容 / 沉淀

规则：同一份简历内标签词风格统一；「个人贡献：只写本人实际完成的部分；保留仓库、PR、Issue 或作品链接」。

## 四、成果行 XYZ 公式（Google 前人事负责人 Laszlo Bock 推广，行级公式）

四段式管**条目骨架**，XYZ 管**每行成果句**。实现类、产出类的每一行都应满足：

> **达成 [X]，以 [Y] 度量，通过 [Z] 完成。**（Accomplished [X] as measured by [Y], by doing [Z]）

- X = 成果（强动词开头）；Y = 数字证据（百分比/金额/时间/规模）；Z = 具体做法（含技术/方法，天然命中 JD 关键词）。
- 缺 X = 流水账；缺 Y = 不可信；缺 Z = 像碰运气。
- 示例：「接口 TP99 从 3.2s 降至 120ms（Y），通过添加复合索引与查询改写（Z）解决订单查询全表扫描问题（X）」。
- 找不到 Y 时按四问挖：**钱**（省了多少成本）？**时间**（周期从多久缩到多久）？**质量**（错误率/满意度）？**规模**（服务多少人/多少数据）？真没有就 `[~X%]` 估算标注。

## 五、强动词与禁用词

- **禁用开头**：负责 / 参与 / 协助 / 配合 / 完成 / 打杂 / 熟悉
- **推荐替换**：主导 / 重构 / 搭建 / 推动 / 设计 / 落地 / 沉淀 / 编排 / 攻坚 / 收口
  （「参与」并非绝对禁用——描述协作边界时可用「参与需求拆解、…联调」这类具体动作列表）

## 五、量化维度速查（按岗位类型选 1-2 个切入）

| 岗位类型 | 常用量化维度 |
|---|---|
| 研发/算法 | QPS、P95/P99 延迟、错误率、模型指标（准确率/F1/召回）、token 成本、构建时长 |
| 产品/运营 | GMV、DAU/MAU、转化率、留存率、CAC/LTV、ROI、活动覆盖人数 |
| 数据 | 数据量级、任务时长、报表产出周期、口径统一覆盖的业务线数 |
| 设计 | 改版后转化/任务完成率、组件库覆盖率、交付周期缩短 |
| 通用 | 人数（带队/协作规模）、周期（提前交付 N 天）、频次（周报→自动化日报） |

无确切数字时：写 `[~X%]` 标注待验证估算并提醒用户核实；**绝不编造精确数字**。

## 七、技术岗补充约定（吸收自 JavaGuide / ResumeSample 等高星开源简历指南）

- **技术栈分层**：技能标签按「语言 → 框架 → 数据库/中间件 → 工具链」分层，每层按精通/熟练/了解标注；熟练度必须与项目经历互相印证（写了「精通 Kubernetes」就要有 K8s 项目支撑），忌堆砌 10+ 技术。
- **版本与方案具体性**：写清版本与方案（「基于 Spring Boot 2.7.x 集成 Spring Security OAuth2 实现 JWT 认证」而非「使用 Spring Boot 开发后端」）；技术选型给理由（为什么 Redis 集群而不是单机：QPS、高可用、成本）。
- **开源贡献格式**：项目名 + 链接 + 一句话介绍（功能+技术栈）+ Star 数 / PR #编号（已合并）。只写经得起点开检查的内容。
- **ATS 硬规则**：关键内容不用表格/图片承载；缩写首次出现写全称（Kubernetes 而非只写 K8s）；输出标准 PDF；文件名「姓名-岗位.pdf」。
- **页数**：1-3 年经验严格一页；5 年以上/架构师最多两页。

## 八、自检清单（交付前逐条过）

- [ ] 每条经历四段齐全（或有意省略并有理由）
- [ ] Owner / 0→1 还是 1→100 / Scope 三要素可答
- [ ] 全文无「负责/参与」开头（或仅用于边界声明）
- [ ] 每行 ≤80 字符；标签词全文统一
- [ ] 指标可核验或已标 `[~X%]`；无编造的学校/公司/头衔
- [ ] 技能标签具体到工具与技术点，非笼统短语
- [ ] 技术栈分层且熟练度与项目互相印证；版本/方案写具体
- [ ] 每行成果句 X/Y/Z 齐全（或缺 Y 有 `[~X%]` 标注）
